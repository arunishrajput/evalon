# Phase 1 Report — Foundation

## What was built

- `backend/app/database.py` — async SQLAlchemy engine/session factory and the
  shared `Base`. `Base.type_annotation_map` maps `datetime` → `DateTime(timezone=True)`
  globally, so every `Mapped[datetime]` column across all 12 models is
  `TIMESTAMPTZ` by construction rather than by per-column discipline.
- `backend/app/models/` — all 12 ORM models from spec Section 5, grouped into
  the 9 files the spec's directory listing names (`hackathon.py` holds
  `Hackathon` + `HackathonParticipant` + `HackathonStats`; `chat.py` holds
  `ChatSession` + `ChatMessage`). A small `UUIDPKMixin` / `CreatedAtMixin` /
  `UpdatedAtMixin` in `models/base.py` removes the boilerplate that would
  otherwise repeat across all 12 tables.
- `backend/alembic/` — async-aware `env.py` (migrations run through
  `create_async_engine` + `connection.run_sync`), and the initial migration
  creating all 12 tables plus every index Section 5 requires, including the
  composite `(hackathon_id, status)` / `(evaluation_id, agent_id)` /
  `(hackathon_id, rank)` indexes and an **HNSW** index on
  `repo_embeddings.embedding` using `vector_cosine_ops`.
- `docker-compose.dev.yml` — override file for running the full stack in
  Docker with debug-friendly settings (CLAUDE.md's primary `make dev` workflow
  — postgres+redis in Docker, backend/frontend native — doesn't need it, but
  the spec requires the file and it's genuinely useful for full-container
  debugging).
- `backend/app/jobs/worker.py` + `jobs/tasks.py` — a real (not stubbed) ARQ
  `WorkerSettings` with one task, `ping`. ARQ refuses to start a worker with
  zero registered functions, and the domain jobs (`ingest_repository`,
  `run_evaluation_pipeline`, etc.) don't exist until Phases 3–6 — `ping` is a
  genuine, working diagnostic task (not a fake placeholder) that lets the
  worker container run cleanly now and proves the queue round-trips.
- Wired up the real database health check in `GET /api/v1/health` (Phase 0
  had it hardcoded to `false` with a documented TODO — now a live `SELECT 1`).

## Architectural decisions

- `Base.type_annotation_map` for timezone-aware datetimes globally, rather
  than repeating `DateTime(timezone=True)` on every column — caught and fixed
  during this phase (the first autogenerated migration produced naive
  `TIMESTAMP` columns, which violates spec Section 5's "all timestamps stored
  in UTC" requirement).
- Composite/HNSW indexes are declared in the ORM models (`__table_args__`),
  not hand-edited into the migration, so `alembic revision --autogenerate`
  stays a reliable source of truth for future schema changes instead of
  drifting from what the models declare.
- The initial migration explicitly runs `CREATE EXTENSION IF NOT EXISTS vector`
  as its first statement (idempotent) in addition to the postgres init script
  bootstrapping it — makes the migration self-sufficient against any Postgres
  target, not just this repo's Compose setup.

## Known issues / technical debt

- **pgvector + Alembic autogenerate quirk**: the autogenerated migration
  referenced `pgvector.sqlalchemy.vector.VECTOR` without importing
  `pgvector.sqlalchemy`. Fixed by hand-adding the import to the generated
  file. This will resurface on any future autogenerate that touches a
  `Vector` column — documented in `DEBUGGING_GUIDE.md` (Phase 8) as a known
  gotcha, not something worth building custom Alembic tooling around for an
  MVP.
- `npm install` during the frontend image build reports 16 vulnerabilities
  (15 high, 1 critical) in transitive dependencies, largely from the pinned
  Next.js 14.2.18 / ESLint 8 lineage the spec specifies. Tracked for Phase 7
  polish; not blocking since no submitted-repo content ever reaches the
  frontend build process (only cloned-repo *text* is processed server-side,
  per P4 — never executed).
- `GET /api/v1/admin/hackathons` and `GET /api/v1/admin/queue/status` remain
  unimplemented, now blocked only on Phase 2 (hackathon CRUD) and Phase 3
  (ARQ job introspection) respectively.
